01
Project Overview

Nexus360 is an AI agent that gives non-technical users natural language access to a live Salesforce CRM. A sales manager can type "What is the health of Acme Corp?" and receive a structured answer drawn from real Salesforce data. A support lead can say "Create a high priority case for Globex Inc about database timeouts" and it happens — the case is created in Salesforce, but only after the user explicitly approves the action.

The project is built across four deliberate phases, each solving a problem the previous phase exposed. It is not a prototype with mock data — every query runs live SOQL against a Salesforce Developer Org, every write operation touches real records, and every conversation turn is persisted to a production Supabase database.

The goal was never to build the most complex agent. The goal was to build one that demonstrates clear thinking about where agents go wrong and how to fix it — which is exactly what production agent engineering requires.

What the agent can do

Capability How it works Source
get_account_health Returns revenue, open cases, and pipeline for any account Salesforce SOQL
list_open_cases Lists all non-closed cases with priority and status Salesforce SOQL
search_knowledge_base Retrieves relevant policy and playbook excerpts Qdrant RAG
update_opportunity_stage Moves a deal to a new pipeline stage (requires approval) Salesforce API
create_support_case Logs a new support case (requires approval) Salesforce API
02
Why This Project

The Salesforce Agentforce Engineer role sits at the intersection of three things most candidates can only talk about: building agents that use tools, connecting those agents to Salesforce, and understanding where agents break in production environments. Nexus360 is a working demonstration of all three.

It uses the actual Salesforce platform the interviewer works with every day. It shows a real agent failure — not a hypothetical one — and a real fix. It uses LangGraph, the current standard for production agent architecture. And it is built end-to-end: Python backend, React frontend, live data, full observability.

There is also a hardware constraint worth noting. This project runs on an i5-9300H with 8GB RAM and a GTX 1050. Every architectural decision that involves inference was made with this constraint in mind. Groq was chosen over local models precisely because it delivers 70B parameter quality at hardware-agnostic speed, which reflects a real production concern: cost and infrastructure efficiency in agentic systems.

03
Architecture

The system has three layers: a React frontend that manages session state and renders the approval UI, a FastAPI backend that handles HTTP routing and request validation, and a LangGraph agent graph that orchestrates reasoning, tool use, validation, and memory.

React UI (TypeScript)
  ↓ POST /chat { message, session_id }
FastAPI (Python)
  ↓ run_agent(message, session_id, approved)
    Load history from Supabase → prepend to messages
    ↓
LangGraph StateGraph
  ├── reason       → LLM decides which tool to call
  ├── validate     → sanitize inputs, classify READ / WRITE
  ├── human_approval → WRITE ops pause here
  ├── execute     → ToolNode runs the tool
  ├── respond     → LLM formats tool output
  └── save_memory  → persist turn to Supabase
    ↓
Tools
  ├── Salesforce (simple-salesforce → SOQL)
  ├── Qdrant Cloud (cosine similarity search)
  └── Supabase (conversation persistence)
    ↓
LangSmith (full trace of every run)

State management

The agent graph is stateless between invocations — every call to run_agent() builds a fresh State object. Conversation continuity is achieved by loading the last 10 messages from Supabase and prepending them to the message list before the graph starts. This design means the agent scales horizontally without sticky sessions, and memory can be inspected or modified directly in the database.

# State shape — the contract between all 6 nodes class State(TypedDict): messages: Annotated[list, add_messages] # append-only session_id: str # UUID from frontend pending_tool: dict | None # write op awaiting approval approved: bool | None # None=waiting, True=go, False=block final_output: str # the answer returned to the user
04
The 4-Phase Story

Each phase is not a feature addition — it is a response to a specific failure or limitation identified in the previous phase. This progression is the core narrative of the project.

Foundation
Real connections, real data

Salesforce Developer Org connected via simple-salesforce. Groq API verified. 8 accounts, 8 opportunities, 8 cases seeded. 4 SOQL-backed tool functions built and tested against live data. No mock data anywhere in the project from this point forward.

Phase 1
Naive agent — works, but unsafe

LangGraph prebuilt ReAct agent wired to all 4 tools. FastAPI /chat endpoint. React dark terminal UI. The agent correctly answers questions — but it also fires write operations immediately with no validation. Trailing punctuation breaks account lookups. No memory between turns.

Phase 2
Guardrails — custom LangGraph graph

Replaced prebuilt agent with a custom StateGraph. Tools split into READ and WRITE sets. Validate node sanitizes inputs and routes writes to human_approval. Frontend shows an amber approval card with the exact tool and arguments. User must click Approve before any Salesforce write executes.

Phase 3
Memory + RAG — stateful and grounded

Supabase stores every conversation turn keyed by UUID session_id. History loaded before each graph run — correct ordering guaranteed by loading in run_agent() rather than as a graph node. Qdrant Cloud stores 8 internal knowledge base documents. Agent correctly cites source — Salesforce or knowledge base — in every response.

Phase 4
Polish — observable, documented, demo-ready

LangSmith tracing added — two env variables, zero code changes, full visibility into every node, token count, and latency. README written with full setup instructions. requirements.txt generated. Architecture diagram, interview talking points, demo script, and this report produced.

05
Technical Decisions
Decision — Groq over local models or OpenAI

Hardware constraint: GTX 1050 4GB VRAM cannot run a 70B model locally. OpenAI adds cost and vendor lock-in. Groq's free tier delivers llama-3.3-70b-versatile at inference speeds that feel instant, with a generous rate limit suitable for a demo. This is also a signal of production cost-awareness — Groq's architecture is purpose-built for LLM inference efficiency.

Decision — LangGraph over LangChain AgentExecutor

AgentExecutor is deprecated in LangChain 1.x. More importantly, AgentExecutor is a black box — you cannot inspect or control what happens between tool calls. LangGraph exposes every step as an explicit node with typed state. This is not just a technical upgrade — it is the difference between an agent you can reason about and one you cannot. For production systems this distinction is critical.

Decision — History loaded in run_agent(), not as a graph node

The first implementation loaded conversation history inside a load_memory graph node. This caused a subtle ordering bug: the current message was appended to initial_state first, then history was appended after it by the node. The LLM saw messages in reverse chronological order and answered the previous question instead of the current one. Moving history loading into run_agent() before the graph starts guarantees correct ordering: [history] + [current message], always.

Decision — Session IDs as UUIDs generated in the browser

Each React app load generates a UUID via crypto.randomUUID(). Same tab = same conversation. New tab = fresh memory. A NEW SESSION button regenerates the UUID without reloading the page. This is the right default for a CRM assistant: a sales rep opening the app in the morning should start clean. The production upgrade path is straightforward — link session_id to the authenticated Salesforce user ID so memory persists across devices.

Decision — Tools return plain strings, not structured dicts

The LLM receives tool output as text and reasons over it. Structured plain text (labelled fields, clear formatting) consistently produces better LLM reasoning and cleaner final answers than raw JSON dicts. It also makes the Observation step in the ReAct trace human-readable, which matters for debugging and for explaining agent behaviour in an interview.

06
Challenges and Solutions
Dependency LangChain 1.x removed AgentExecutor from the public API
Problem

Attempted to downgrade LangChain to 0.2.x to restore AgentExecutor. This broke langchain-groq and langgraph which required langchain-core ≥1.2.8. Dependency conflict with no clean resolution.

Solution

Stayed on LangChain 1.x and switched to langgraph.prebuilt.create_react_agent for Phase 1. This was ultimately the better outcome — it forced the Phase 2 architecture to be LangGraph-native from the start, which is what Salesforce uses in production Agentforce.

State unhashable type: 'SystemMessage' crash
Problem

LangGraph tried to merge state updates by hashing messages. SystemMessage objects are not hashable, causing a crash on every graph invocation when messages were defined as a plain list in State.

Solution

Changed State to use Annotated[list, add_messages] which tells LangGraph to append rather than replace. Moved SystemMessage out of state entirely — it is now constructed locally inside each node and passed directly to llm.invoke(), never stored in state.

Logic Approval state immediately rejected on first call
Problem

The human_approval node treated approved=None as rejected (fell through to the else branch). Write operations were blocked immediately instead of pausing for user input. The approval card never appeared in the frontend.

Solution

Added an explicit None check as the first branch: if approved is None, return without executing. The graph ends and returns pending_tool to the frontend. The user then calls /approve or /reject which re-runs the graph with the decision set.

Logic Validate node overwrote approved=True on re-run
Problem

When /approve re-ran the graph with approved=True, the validate node detected a WRITE tool and set approved=None again, overwriting the approval. The graph looped back to human_approval and blocked the action a second time.

Solution

Added an early return at the top of validate: if state["approved"] is True, skip the write check and return approved=True immediately. This preserves the approval decision across the full graph run.

Memory Agent answered the previous question instead of the current one
Problem

History was loaded inside a load_memory graph node. The current HumanMessage was set in initial_state first, then history was appended after it by the node. The LLM received messages in reverse order and responded to the previous turn.

Solution

Removed the load_memory node entirely. History is now loaded in run_agent() before initial_state is constructed: history messages are built first, then the current message is appended last. Correct ordering is guaranteed structurally, not at runtime.

API Qdrant .search() method removed in newer client versions
Problem

QdrantClient.search() was deprecated and removed in newer versions of the qdrant-client library. Collection creation and document upsert succeeded but every search call failed with AttributeError.

Solution

Replaced .search() with .query_points() and appended .points to the result to extract the list. The new API is more explicit and consistent with Qdrant's direction toward a unified query interface.

07
Observability

Observability was not part of the original plan and was identified as a gap during the Phase 4 audit. For any AI agent running in production, the ability to inspect what happened — which nodes ran, what the LLM received, how long each step took, which tools were called and with what inputs — is not optional. It is the difference between a system you can debug and one you cannot.

LangSmith tracing was added at the end of Phase 3. The implementation required two environment variables and zero code changes — LangChain automatically detects LANGCHAIN_TRACING_V2=true and sends a full execution trace to the configured project on every graph.invoke() call.

# .env — all that is needed for full LangSmith tracing LANGCHAIN_TRACING_V2=true LANGCHAIN_API_KEY=your-key LANGCHAIN_PROJECT=nexus360

Every trace in LangSmith shows the full graph execution tree — which conditional edge was taken, the exact messages sent to the LLM at each node, tool call inputs and outputs, token usage per step, and end-to-end latency. This is the foundation for the next observability upgrade: setting latency thresholds, alerting on tool failures, and tracking which knowledge base documents are retrieved most frequently.

08
Production Roadmap

Nexus360 in its current form is a fully functional local demo. The following changes would be required to deploy it as a production system.

1

Authentication

Add OAuth2 or JWT authentication to the FastAPI endpoints. Link session_id to the authenticated Salesforce user ID so memory persists across devices and is scoped per user. The Supabase conversations table would get a user_id column and Row Level Security enabled.

2

Streaming responses

Both FastAPI (Server-Sent Events) and LangGraph (astream()) support streaming. Adding it requires changing the /chat endpoint to return a StreamingResponse and updating the React frontend to consume the event stream. The user experience improvement is significant — responses appear token by token instead of all at once after a multi-second wait.

3

Fuzzy account name matching

Currently, "Acme Corp." (with a period) fails to match "Acme Corp" in Salesforce. The production fix is to embed all Salesforce account names into Qdrant at startup and perform a semantic similarity search before running the main SOQL query. This makes the agent robust to typos, abbreviations, and variations — which is how real users type.

4

Persistent approval state

Currently the pending_tool is held in React state — a browser refresh loses the pending approval. In production, pending write operations would be persisted to Supabase with a status field (pending / approved / rejected) so they survive page reloads and can be reviewed asynchronously.

5

Embedding service as a separate microservice

The SentenceTransformer model currently loads when the FastAPI process starts. In production, this would be a separate FastAPI service running on a GPU-enabled instance, exposing a /embed endpoint. The main agent calls it over HTTP. This prevents the embedding model from adding cold-start latency to every agent restart and allows it to scale independently.

6

Salesforce Connected App with OAuth

The current integration uses username + password + security token — acceptable for a dev org but not for production. A Salesforce Connected App with OAuth 2.0 JWT Bearer Flow is the correct pattern for server-to-server authentication in a production deployment.
